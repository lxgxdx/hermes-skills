## 模式 1：三向闭环（v8 二向 → v9 三向）—— Wiki 政策库 ↔ cron 选题 ↔ cron Wiki 选政策

**v8 已记录的二向循环**（`references/cron-v8-validations.md` 模式 2）：

```
[Wiki 政策页]  →  cron 01:00 读 Wiki  →  [制度漏洞选题]  →  [信息稿]  →  [Wiki 政策页]
```

**v9 6/9 实证的第三向**：

```
[Wiki 政策页]  →  cron 01:00 读 Wiki  →  [制度漏洞选题]
   ↑                                              ↓ cron 选题热度（民族宗教方向最热）
   │                                              ↓
   └────  cron 01:30 选政策深化  ←──── 反向选 P01 宗教政策索引页
```

**6/9 实证细节**：
- 6/9 01:00 cron 生成的 5 选题中，"民族宗教方向"占比最高（6/8 选题已包含 P01
  宗教政策关联的 3 个制度漏洞富矿）
- 6/9 01:30 cron Wiki 选政策时，**优先选了 `policy-religion-regulations.md`**
  （P01 索引页）做案例深化
- 决策依据：cron 内置"读上一日选题 → 提取热度最高领域 → 选对应政策深化"
  隐式启发式（未显式编码，但 agent 在两轮 cron 间可观察到这个规律）

**通用三向闭环规则（适用于任何"知识库 + cron 触发器"组合）**：

| 方向 | 信号 | 触发器 |
|------|------|--------|
| Wiki → cron 选题 | Wiki 政策页"执行层面问题标注" | cron 01:00 读 `~/wiki/entities/policy-*.md` |
| cron 选题 → Wiki 选政策 | 上一日选题热度最高的领域 | cron 01:30 选 `policy-<领域>.md` 深化 |
| Wiki 深化 → 反哺 cron | 新案例/新制度问题点 | 下一轮 cron 01:00 又读到新富矿 |

**对 user-profile-curation 的影响**：

- v(n) 报告 Wiki 进展时，**必须列出 3 个闭环节点**（不是只列 Wiki 深化数）：
  1. Wiki 政策库深化了哪些页
  2. cron 01:00 从这些页挖出了哪些制度漏洞选题
  3. cron 01:30 下一轮选了哪个政策深化（隐式热度驱动）
- v(n+1) 报告 cron 选题时，**必须标"本轮选题热度排名 + 下轮 Wiki 选政策预测"**——让
  闭环可见、可审计

**对 tongzhan-info-workflow / tongzhan-wiki-policy-builder 的影响**：

- tongzhan-wiki-policy-builder 的"选政策"逻辑**应升级**为：
  1. 读 `references/选题排重规则.md` 第四节"近 3 天每日选题"
  2. 统计"民族宗教 / 台湾 / 工商联 / 党外人士"等领域热度排名
  3. 优先选热度最高领域对应的 policy-*.md 深化
  4. 优先级：`policy-<领域>.md` 已深化 → 走"路径② 索引页案例深化"（见模式 2）
- 现状（v9 6/9）：agent 是隐式按这个规则选的；下一个 skill 版本应显式编码

## 模式 2：Wiki 政策深化路径分两种（v9 6/9 实证）—— 母法本身 vs 索引页案例深化

**v8 `references/cron-v8-validations.md` 隐式假定**只有一种路径：
"母法本身深化 + `comparisons/` 案例库子页"（P15 光彩事业章程 + P05 台湾同胞投资保护法）。

**v9 6/9 实证的第二种路径**：

P01 `policy-religion-regulations.md` **本身是索引页**（不是单一法律），深化方式：
- 不动索引页结构
- 新增 3 条 2026 年真实案例（李干杰 2026-04 甘川调研承认基层短板、佛教中国化五年
  规划纲要 2023-2027 软硬法边界、注销戒牒公告退出机制）
- 新增"案例间制度逻辑串联图 + 3 条核心制度问题总结"
- 案例标在 `sources:` 字段，body 内加 "## 三、2026 年真实案例" 章节

**两条路径对比**：

| 维度 | 路径 ① 母法本身深化 | 路径 ② 索引页案例深化 |
|------|-------------------|---------------------|
| 适用对象 | 单部法律（如 P15 章程、P05 投资法） | 索引页/合集页（如 P01 宗教法规索引） |
| 工作量 | 高（5 类制度问题 + 6 条案例 + 20+ 行） | 中（3 条案例 + 串联图 + 10+ 行） |
| 价值 | 制度问题+案例双富矿 | 案例为主，制度问题为辅 |
| 复用度 | 可建 `comparisons/` 子页 | 不必建子页（案例直接入索引页 body） |
| 适用 cron 时间窗 | 01:30 整段（约 90 条消息预算） | 01:30 整段（约 90 条消息预算） |

**v9 暗示**（关键决策点）：

- 未来 P01/P10/P11/P12/P13 等浅页可走"路径 ② 索引页案例深化"
- 路径选择启发式：
  - 政策页 = 单部法律 → 路径 ①
  - 政策页 = 索引页 / 合集 / 法规汇总 → 路径 ②
  - 政策页既有母法也有合集 → 路径 ① + 在 body 末尾加 "## 子法/合集" 章节走 ②

**对 user-profile-curation 的影响**：

- v(n) 报告 Wiki 进展时，**必须标"深化路径"**：①/②/混合
- v(n) 报告 Wiki 浅页转化时（P01 → P10 → P11...），**预期都是路径 ②**
- Wiki 路径 ② 的 cron 01:30 模板可独立于路径 ① —— 值得单独抽 skill 子模板

## 模式 3：连续 cron 日天花板 = 8 日（v9 6/9 实测，刷新 v8 的 7 日记录）

**v8 假设的天花板**（`references/cron-v8-validations.md` 模式 3）：

> 1-5 日：正常范围
> 6-7 日：v(n) 报告应明确"累计 X 天无人类对话"提示
> ≥ 8 日：v(n) 报告应在"洞察"章节加 USER ALERT

**v9 6/9 实测**：连续 8 日全 cron（6/2 → 6/9）零人类对话，**未观察到** cron 质量明显下降
或用户失联信号。**8 日是新的"软上限"**，不一定是硬上限。

**修正后的阈值建议**（取代 v8 阈值）：

| 连续 cron 日数 | v(n) 报告应包含 |
|----------------|----------------|
| 1-5 日 | 正常范围，无需特殊提示 |
| 6-7 日 | 在 v(n) 增量章节加 "累计 X 天无人类对话" 一行 |
| 8-10 日 | 在"洞察"章节加 "USER CHECKPOINT 建议"：列出累计产出的核心文件清单 + 建议下次人类对话时先回顾 |
| ≥ 11 日 | 升级为 USER ALERT：飞书 webhook 若仍失效，应视为"用户可能不知情所有 cron 产出" |

**关键观察**：v9 8 日 cron 期间，cron 内部产出质量**未降反升**：
- 6/8 → 6/9 选题 cron 连续两日成功（累计 10 选题）
- 6/8 → 6/9 Wiki 政策深化连续两日完成（P05 案例库 + P01 索引页案例）
- 模式 1（三向闭环）在 6/9 自然涌现
- 模式 2（路径 ② 索引页案例深化）在 6/9 首次出现

**这说明**：cron 自主性上限**不是 7 日也不是 8 日**，可能是用户 webhook 失效导致的
"不知情上限"——cron 本身没问题。

**对 user-profile-curation 的影响**：

- v(n) 报告应**不再写"7 日天花板"**，改写"≥ 8 日用户 checkpoint 建议"
- v(n) 报告的"洞察"章节应包含 cron 健康度判断（基于 webhook 状态 + cron 内部产出质量）
- v(n+1) 报告应在 user 终于回归时附"你错过了什么"累计产出摘要
